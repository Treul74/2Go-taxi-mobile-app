Read-Only Architecture Audit

The navigation system, as it actually runs today

A file-by-file audit of every map, camera, GPS, and routing code path in the 2Go app — driver and passenger — prepared as groundwork for a single, reusable navigation engine. No code was changed to produce this report.

61 files inspected 3 platforms: iOS · Android · Web Expo SDK 54 · react-native-maps · Zustand 2026-08-02

Executive Summary

The app does not have one navigation system — it has three. The map rendering layer is well-factored; the camera and routing logic layered on top of it is not.

The rendering layer — Map.native.tsx, its markers, and the Reanimated-driven useAnimatedMarker hook — is the one part of this system that already looks like a reusable engine. It is undermined from above: three screens (navigate.tsx, (driver)/navigation.tsx, (driver)/trip.tsx) each hand-roll their own copy of the Google-Maps-style heading-up follow camera, each with slightly different fallback logic and none sharing a hook. There is no camera-state store, no shared route-fetch hook, and no shared GPS-watch hook — every screen that needs a driver's live position starts its own watchPositionAsync subscription from scratch. The passenger's own trip screen (app/(customer)/trip.tsx) has no camera logic at all and no polyline, which is the single biggest reason the ride doesn't feel like Uber or Yango on the passenger side — there is nothing there generating that experience yet, not a bug suppressing it.

01Current Navigation Architecture

Seven screens render a map. All but one funnel through the same native component — but each screen re-derives its own navigation behavior on top of it.

Six of the seven map-bearing screens render the shared Map component (resolved by Metro to Map.native.tsx on device, Map.web.tsx on web). The seventh, MapPickerModal.native.tsx, bypasses it entirely and constructs its own react-native-maps MapView — duplicating the native-module lazy-require guard, the initial-region shape, and the zoom-delta constants that already live in Map.native.tsx. It has no navigation behavior itself (it's a drag-to-pick-a-point picker), so the duplication is contained, but it's a second map-construction code path that the audit found no reason for.

The rendering layer itself is sound

Map.native.tsx is a genuinely well-built component: a forwardRef with an imperative handle (animateToRegion, animateCamera, fitToCoordinates, getMapRef), three internal auto-camera effects, zoom controls, H3 debug overlay, and a marker layer driven by Reanimated. The marker components (AnimatedVehicleMarker, AnimatedUserLocation, NavigationArrowMarker) all funnel through one shared hook, useAnimatedMarker, which does the actual work of gliding position and rotating heading along the shortest arc on the UI thread. That hook is the one piece of this system that already looks like the "engine" the redesign is aiming for — it's just scoped to markers, not the camera.

Map.web.tsx is a parallel, materially thinner reimplementation: it is not wrapped in forwardRef, so any mapRef.current?.animateCamera(...) call from a parent screen silently no-ops on web (React drops the ref with a dev warning). It also has no navigationArrowMode, no vehicle fleet rendering, no H3 overlay, no ETA badge, and no Reanimated-driven marker glide — the driver icon on web is a statically-rotated view. Web is not a lost cause (the underlying `` supports everything native does), but today it is a second, much smaller implementation, not a platform variant of one engine.

02Current Camera Architecture

Nobody owns the camera. Up to four independent writers can target the same mapRef depending on which screen is mounted.

Ownership, screen by screen

(driver)/trip.tsxYesYes → false while navigatingYes — own effect, richer bearing fallback
(tabs)/navigate.tsxYesYes → conditional on isNavigatingYes — inline in GPS callback

Map.native.tsx defaults autoFollowDriver to true. Every screen that passes a driverLocation prop without explicitly turning that off inherits an automatic animateToRegion recenter on every GPS fix, running underneath whatever camera logic the screen itself owns. The three driver-navigation screens know about this and turn it off. DriverDashboard.tsx does not — it runs its own animateToRegion call inside its GPS callback (600ms) while Map.native.tsx's own effect fires the same call (500ms default) on the same event, targeting the same region. It's low-stakes today because both calls compute the same destination, but it's two writers doing the same job for no reason, and the pattern is what causes the camera to feel like it's "fighting itself" — a symptom, not the root problem.

Why it doesn't feel like Uber

Three separate heading-up implementations, not oneCritical

navigation.tsx, trip.tsx, and navigate.tsx each independently call animateCamera({center, heading, pitch: 45, altitude: 500, zoom: 17}, 700) — same shape, same constants, three different files, three different heading-fallback strategies (none / bearing-to-next-maneuver-if-heading≤1 / bearing-to-next-maneuver-if-heading<1). Any tuning pass ("make the follow feel smoother") has to be applied three times and will drift the moment one file is edited and the others aren't.

app/(driver)/navigation.tsx:238–252 · app/(driver)/trip.tsx:248–272 · app/(tabs)/navigate.tsx:101–123

The passenger never gets a navigation camera at allCritical

(customer)/trip.tsx has no mapRef, no heading, no pitch, no polyline. The only camera behavior it gets is Map.native.tsx's default flat recenter-on-driver-move. This is the single largest gap between the current app and an Uber/Yango-style experience — the customer-facing trip screen is the one screen a rider spends the most time looking at, and it currently has zero navigation-camera code written for it.

app/(customer)/trip.tsx — no mapRef declared anywhere in the file

Two fits can race in the same windowModerate

In navigate.tsx, Map.native.tsx's own internal "fit to pickup+destination" effect and navigate.tsx's own calculateRoute()-triggered fitToCoordinates call are both wired to the same pickup/destination change, with different edge padding and different coordinate sets (two endpoints vs. the full route polyline). In practice Map.native.tsx's effect self-excludes once driverLocation is populated, so the window is narrow — but it exists on fresh mount, before the first GPS fix, if a previous start/destination is already remembered.

src/components/map/Map.native.tsx:220–243 vs app/(tabs)/navigate.tsx:148–172

The zoom-delta pair latitudeDelta: 0.0035, longitudeDelta: 0.0016 ("street-level zoom") is a bare literal in at least 8 places across Map.native.tsx, PassengerHome.tsx, DriverDashboard.tsx, and MapPickerModal.native.tsx. NAV_CAMERA_PITCH/ALTITUDE/ZOOM (45/500/17) are declared as named constants independently in two files and inlined as raw numbers in a third.

03Current Routing Architecture

Four independent call sites hit the Google Directions API. Recalculation policy differs screen to screen, with no shared debounce.

Recalculation policy is inconsistent by accident, not design

CallerRecalculates whenDebounced?
RidePlannerSheet.tsx:150–172pickup/destination change (any amount)No
(tabs)/navigate.tsx:142–172Selection change, while not navigatingNo
(driver)/navigation.tsx:119–147Once — guarded by routeCoordinates.length === 0N/A (fires once)
(driver)/trip.tsx:181–198Every GPS fix — no guard beyond a race-safety cancel flagNo

The Directions call itself is centralized correctly — every one of these four sites goes through the same getDirections() in src/lib/google/mapsApi.ts, which does the actual polyline decoding via @googlemaps/polyline-codec. What isn't centralized is when to call it. trip.tsx's effect depends on driverLocation.lat/lng and re-fires on every accepted fix from a 1-second-interval GPS watcher — in the worst case that's a live Directions API call roughly once per second for the duration of a trip, guarded only by a cancelled flag for race safety, not a rate limit or distance-moved threshold. navigation.tsx solves the same underlying problem (driver moved, does the route need updating?) with a one-shot guard instead, which means it will show a stale route if the driver goes off-route. Neither is wrong for its own screen in isolation; the risk is that a future change to one will not propagate to the other three, because there's no shared policy to change.

src/lib/google/mapsApi.ts itself has no caching, memoization, or client-side rate limiting anywhere — every exported function (getDirections, getPlaceAutocomplete, geocodeAddress, reverseGeocode, getDistanceMatrix, snapToRoads) is a direct, uncached fetch. Error handling is consistent (try/catch, log, safe fallback — never throws except on a missing API key), which is good hygiene, but it also means nothing stops a caller from hammering the endpoint the way trip.tsx's effect currently can.

Road-snapping is two different things wearing similar names

useRoadSnappedVehicle snaps a moving vehicle's GPS fix onto an already-fetched route polyline using local point-to-segment projection math (no network call) — used to smooth the driver marker. useSnappedLocation snaps the customer's own position onto the nearest real road via a paid Google Roads API call — used only by PassengerHome for the map display. They solve genuinely different problems for different actors, but the naming makes them easy to confuse, and routeSnapping.ts's general-purpose calculateBearing() — used in four unrelated files — is bundled inside the same module as the polyline-snapping algorithm it has nothing to do with.

04Current GPS Architecture

Five independent watchPositionAsync subscriptions. No shared hook, no shared accuracy policy, no leaks found — but two screens tear down and restart their watcher on every UI toggle.

LocationAccuracy / intervalEffect depsCleanup
useCurrentLocation.ts:94Balanced · 60s / 50m[] — mounts onceCorrect — isMounted guard + subscription.remove()
(driver)/navigation.tsx:82BestForNavigation · 1s / 1m[] — mounts onceCorrect
(driver)/trip.tsx:148BestForNavigation · 1s / 1m[] — mounts onceCorrect
(tabs)/navigate.tsx:80BestForNavigation · 1s / 1m[isNavigating, isAutoFollow]Correct, but the whole watcher is torn down and recreated on every toggle
DriverDashboard.tsx:1053-tier fallback: High → Balanced → Low[isOnline, isAutoFollow]Correct, same tear-down-on-toggle pattern

No leaks and no duplicate concurrent watches were found — every subscription is properly stored in a ref/variable and removed in its effect's cleanup function. The design issue is different: there is no shared "watch my location" hook with a configurable accuracy profile, so five files each re-derive the permission request → initial fix → watcher → fallback sequence independently, with genuinely different accuracy tiers and intervals that were presumably each tuned for their own screen's needs but were never reconciled into an explicit policy (e.g. "planning" screens get Balanced/60s, "actively navigating" screens get BestForNavigation/1s). navigate.tsx and DriverDashboard.tsx additionally key their effect on UI state (isAutoFollow, isOnline) rather than mounting once, which means toggling "follow me" restarts the entire GPS subscription rather than just changing how the existing fixes are consumed — unnecessary permission/watcher churn.

watchHeadingAsync (the device compass API) is never called anywhere in the codebase — heading is always either read off the GPS fix's own heading field or derived client-side via calculateBearing() toward the next route point. This is a reasonable choice (compass heading is noisy at low speed and wrong when stationary) but it means heading quality is entirely dependent on GPS fix quality and the bearing-fallback logic each screen wrote for itself — which, per §2, differs between the three driver-navigation screens.

Separately from all of the above, useDriverTelemetryPing runs its own 5-second setInterval (not a location watcher) that pushes the driver's last-known lat/lng/heading to the backend order row — this is the actual mechanism that makes the driver visible to the passenger in (customer)/trip.tsx, and it is completely decoupled from the on-screen camera-follow GPS watchers described above.

05Problems Found

Consolidated across camera, routing, GPS, state, platform parity, and dead code — ranked by how directly each blocks an Uber/Yango-grade experience.

No navigation camera exists for the passengerCritical

Covered in §2 — repeated here because it is the highest-impact single fact in this audit for "why doesn't this feel like Uber." Nothing needs to be un-broken; a navigation camera and live polyline simply need to be built for (customer)/trip.tsx.

Map.web.tsx silently drops all imperative camera callsCritical

Because it's a plain function component, not forwardRef-wrapped, every mapRef.current?.animateCamera/animateToRegion/fitToCoordinates call from navigate.tsx, trip.tsx, and navigation.tsx no-ops on web with only a dev-console warning. Auto-follow, compass-reset, and route-fit-to-bounds do not function on web today for any of these three screens.

src/components/map/Map.web.tsx — component not wrapped in React.forwardRef

Route recalculates on every GPS fix in trip.tsx, unthrottledCritical

A live Directions API call roughly once per second, for the duration of every trip, is a real cost and a real latency/flicker risk on the polyline. See §3.

app/(driver)/trip.tsx:181–198

Three duplicated heading-up camera effectsModerate

See §2 and §6. Not broken today, but every future camera tuning change has to be applied three times by hand.

Navigation state has no single ownerModerate

Neither rideStore nor driverStore holds camera state, and neither holds turn-by-turn route/step state — that lives only as local useState inside three separate screens. driverStore.tripStatus includes a 'navigating_to_pickup' value, the closest thing to an "isNavigating" flag anywhere, but it isn't shared with rideStore and there's no boolean navigation-mode flag anywhere in the store layer.

src/state/rideStore.ts:51–137 · src/state/driverStore.ts:35–90

Two screens tear down their GPS watcher on every UI toggleModerate

navigate.tsx and DriverDashboard.tsx key their location-watch effect on isAutoFollow/isOnline, restarting the whole subscription (and re-requesting a fix) instead of mounting once. See §4.

Two independent GPS reads feed the same screenModerate

PassengerHome.tsx displays position via the road-snapped useSnappedLocation(), but its own "recenter" button does a separate one-shot getCurrentPositionAsync/getLastKnownPositionAsync read. RidePlannerSheet.tsx auto-populates pickup from raw useCurrentLocation(), not the road-snapped version shown on the map. These can disagree by a small but visible margin.

src/features/passenger/PassengerHome.tsx:229–255 vs :140 · src/features/passenger/components/RidePlannerSheet.tsx:41,123–140

Redundant camera write on DriverDashboardModerate

Map.native.tsx's default autoFollowDriver=true plus this screen's own animateToRegion call both fire on the same GPS event, targeting the same region, at slightly different durations (500ms vs 600ms). See §2.

No caching/rate-limiting on any Google Maps API callInformational

mapsApi.ts issues a direct uncached fetch for every Directions, Places, Geocoding, and Roads call. Not a bug per se, but combined with the unthrottled trip.tsx recalculation above, it's the point where an engine-level fix (shared route hook with built-in debounce) pays for itself directly in API cost.

Web map styling diverges from nativeInformational

mapStyle.ts's custom building/POI styling is applied only in Map.web.tsx — native has no equivalent, so the two platforms render visually differently even where feature parity exists.

Two dead files, confirmed by full-repo import searchInformational

src/assets/svg/NavigationArrow.tsx — a fully-built gradient navigation-arrow icon with zero importers anywhere, superseded by NavigationArrowMarker's simpler inline chevron. src/services/discoveryEngine.ts — operates on a hardcoded mock driver pool, reachable only behind the H3 debug toggle, and never wired into the real matching path (fetchNearbyDriverPushTokens in driverOrders.ts is the real implementation).

09Recommended Global Navigation Engine Architecture

A conceptual target only — no code. The shape below is what the audit above implies is missing, built from the pieces already proven to work.

useCameraController is the piece that doesn't exist today and is the direct answer to the "why doesn't it feel like Google Maps" question — it would encode the handful of camera profiles this audit found scattered across three files (idle recenter, follow, heading-up-navigating, fit-to-bounds) as named, tunable presets instead of ad hoc animateCamera calls, so a single change to "how navigation-mode feels" applies everywhere at once. useRouteEngine would own the one decision every current screen makes differently — when to refetch — as an explicit policy (distance-moved threshold + minimum interval) instead of "once" in one screen and "every fix" in another. useGpsWatch would let a screen declare "I'm in planning mode" or "I'm actively navigating" and get the right accuracy tier without re-deriving the permission/fallback sequence.

A single navigationStore slice would give routeCoordinates/steps/activeStepIndex/isNavigating one home instead of three, and would let (customer)/trip.tsx read the same shape of data the driver screens already produce — the store update, not new per-screen code, is what would let the passenger screen finally show a moving polyline and a following camera.

<NavigationMap> is not a replacement for Map.native.tsx/Map.web.tsx — it's a thin composition layer on top of them that takes a declarative mode ("idle" | "previewing" | "navigating") instead of requiring each screen to hold a mapRef and call imperative methods on it directly. Fixing Map.web.tsx's missing forwardRef is a prerequisite either way, independent of whether this composition layer gets built.

10Phase 2 Roadmap

Ordered so each step is buildable and testable against the current app before the next one starts — nothing here is a big-bang rewrite.

  1. Fix the Map.web.tsx forwardRef gap

    Smallest, highest-leverage fix in the whole audit — every downstream camera-controller step benefits from web not silently dropping camera calls. Independent of everything else below.

  2. Extract the camera-animation module

    Pull the shared shape out of the three existing heading-up implementations (navigation.tsx, trip.tsx, navigate.tsx) into named camera profiles, mirroring how mapAnimation.ts already centralizes marker-animation constants.

  3. Extract the shared GPS-watch hook

    Consolidate the five independent watchPositionAsync call sites behind one hook with an explicit accuracy-profile argument, using useCurrentLocation.ts's cleanup pattern as the template.

  4. Extract the shared route-fetch hook

    One recalculation policy (distance-moved threshold + debounce) replacing the four current ad hoc rules — this directly closes the trip.tsx per-second-refetch issue in §5.

  5. Introduce the single navigation state slice

    Consolidate route/steps/activeStep/cameraMode/isNavigating into one store shape, replacing the local useState copies in the three driver-navigation screens.

  6. Build <NavigationMap> on top of the three hooks above

    The declarative composition layer described in §9, wrapping the already-solid Map.native.tsx/Map.web.tsx — not replacing them.

  7. Migrate (tabs)/navigate.tsx first

    It's already the most feature-complete screen and the only current caller of fitToCoordinates from application code — the best proving ground before touching the two trip-critical driver screens.

  8. Migrate (driver)/navigation.tsx and (driver)/trip.tsx

    Once the engine has been validated on the standalone screen, retire their hand-rolled camera effects and local route state in favor of the shared hooks.

  9. Give (customer)/trip.tsx a real navigation camera for the first time

    This is new capability, not a migration — wire it to the same <NavigationMap>/store the driver screens now use, reading the driver's live position that already flows in via realtime order updates. This is the step that most directly makes the ride feel like Uber/Yango from the passenger's seat.

  10. Collapse marker-wrapper duplication

    AnimatedVehicleMarker/NavigationArrowMarker into one component with a mode prop; UserLocationMarker/SearchPulseMarker's pulse-halo into one usePulseHalo hook. Cosmetic relative to the steps above — do it once the engine underneath has stopped moving.

  11. Sweep dead code and magic constants

    Remove assets/svg/NavigationArrow.tsx and discoveryEngine.ts's mock path (or wire the latter to the real backend if it was meant to ship), centralize the 0.0035/0.0016 zoom delta and NEARBY_HEX_RING constant. Lowest risk, do last so nothing mid-migration depends on the files being removed.

B. Navigation, trip, and picker screens16 files

Full grep inventory of every camera/location call site (fitToCoordinates, animateCamera, watchPositionAsync, animateToRegion) is captured in §2–§4 above.
